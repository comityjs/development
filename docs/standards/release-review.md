# Comity Coding Standards — Release Review of `Version Packages` Pull Requests

> **Provenance:**
> - Authoritative owner: `comity-development`
> - Applies to: every repository that publishes through Changesets (`comity-community`, `comity-development`, future repositories)
> - Status: **Adopted (Accepted) — 2026-11-04**, by Comity maintainer decision, decided as its own item (it did not wait on
>   ADR-033's acceptance). Raised with ADR-033 (Commerce / Comity boundary work, 2026-11-04). Architecture-owner decision D-07:
>   the review is mandatory, with trigger-based depth.
> - **Effect of adoption.** In force from 2026-11-04. This standard is **mandatory for every `Version Packages` pull request**.
>   The **full review (§5) is required only when an objective trigger T1–T6 applies**; otherwise the basic checklist (§4) suffices.
>   **WP-A2** (ADR-033's coordinated patch release) **remains the recommended pilot** and the first calibration use (§5.5).
>   Adoption adds no automation, changes no Changesets configuration or workflow, and **authorises no work package or release**.
> - Enforcement: manual. Each repository applies it in its own release process.

A `Version Packages` pull request is generated by `changesets/action` from the pending `.changeset/*.md` files and merging it
publishes to npm. This standard defines the **mandatory human review** of that pull request. It adds no automation and does not
change Changesets configuration or any workflow; those are separate design decisions (see "Future automation").

## 1. Why the review exists

Changesets assigns bumps by rules the author of a changeset does not see:

- Verified with `@changesets/assemble-release-plan@6.0.10` (the version in comity-community): any package that lists a changed
  package in `peerDependencies` receives a **major** bump when that package gets a **minor or major** release, regardless of the
  declared range (and, with `onlyUpdatePeerDependentsWhenOutOfRange`, whenever the new version leaves the range, which every 0.x
  minor does for a caret range). Under 0.x, a major is `1.0.0`. A **patch** of the peered package does not trigger it.
  **Under the approved release policy (ADR-033, D-01) this cascade is accepted as the default**, not suppressed.
- A sibling dependency with a caret range (`workspace:^`, ADR-033) does not re-release dependents on a sibling **patch**;
  a sibling **minor** re-releases them with a patch bump and moves their ranges.
- `workspace:*` is published as an exact version; `workspace:^` as `^<version at publish>`.

The merge click is the last point at which a wrong range, an unannotated major or a bad publication order can be stopped.

## 2. Roles

| Role | Responsibility |
|---|---|
| **Release reviewer** | A maintainer other than the author of the triggering changesets, where staffing permits. Completes the applicable checklist and records the evidence in the PR |
| **Release owner** | Approves exceptions in §6 and decides how a blocked release proceeds |

Approval of the PR is **not** a substitute for the recorded checklist.

## 3. Review depth: basic checklist for every PR; full review when a trigger applies

### 3.0 Triggers (objectively checkable from the PR diff, the plan and packed manifests)

The **full review (§5)** is required when **any** of the following is true. Otherwise only the basic checklist (§4) is required.

| # | Trigger | How it is checked |
|---|---|---|
| T1 | Any **major** bump, or any `0.x → 1.0.0` transition, in the plan | version diff |
| T2 | Any package in the plan whose `peerDependencies` name a `@comity/*` package that is **also in the plan** (peer-dependent release; includes any minor/major of a peered Core Module) | `peerDependencies` of each package in the plan |
| T3 | Any change to a published **dependency or peer range** or **range protocol** (for example `workspace:*` → `workspace:^`) on a sibling | manifest diff |
| T4 | Any change to `exports`, `main`, `module`, `types`, `typesVersions`, `type`, `bin`, `files` or `engines` (distribution, runtime or package-surface change; ADR-034) | manifest diff |
| T5 | The plan includes `@comity/primitives` (carries `BaseError` runtime identity), or a package is added to, renamed in, or removed from the publishable set | plan / manifest diff |
| T6 | The plan contains **10 or more** packages (initial threshold; see "Calibration") | plan size |

A trigger that cannot be evaluated counts as present.

## 4. Basic checklist (every `Version Packages` PR)

Record each result in a PR comment, with the evidence named.

1. **Package table.** List every package in the plan with old version, new version and bump type (PR diff of `package.json` and
   `CHANGELOG.md`, or `changeset status --verbose`).
2. **Why each package is in the plan:** named in a changeset, or re-released because a dependency changed. Every re-released
   package traces to a changed dependency; an unexplained entry blocks (§7).
3. **Semver class.** Each bump matches the changeset text and the actual change (breaking contract → minor under 0.x with a
   migration note per the package's ADRs; fix → patch).
4. **Packed manifests.** Build and pack each package in the plan (a script that produces the evidence is permitted and should be
   attached); no `workspace:`, `file:` or `link:` specifier remains.
5. **Checks green** on the release branch: build, tests, validation (including declaration/tarball validation of ADR-035 when it
   exists).
6. **Trigger attestation**, one line: *"Triggers T1–T6 evaluated: none present"* — or the list of triggers present and the link
   to the full review.

## 5. Full review (when any trigger T1–T6 applies)

In addition to §4:

### 5.1 Majors and peer-dependent bumps

For every package whose bump is a **major** (T1) or that lists a changed package in `peerDependencies` (T2):

1. State the origin: a named changeset, or the peer dependency that triggered the Changesets peer rule.
2. Classify the major as **contract-driven** (the package's own public contract changed; name the specific changed or removed
   contract) or **peer-driven** (no contract change; the bump exists only because the peered package took a minor/major).
   This classification is judgment, not inspection; the reviewer names the evidence.
3. **Peer-driven majors are accepted by default (ADR-033, D-01).** Each must be listed in the PR, labelled peer-driven, and
   stated as such in the changelog and release notes, including that `1.0.0` is a one-way change. Do not edit the generated
   branch, change Changesets configuration or alter the `version` script to avoid a cascade.
4. Confirm the peer range of every package in the plan, as published, expresses the peered versions it was tested against (§5.2).
5. A split release (publishing the peered package alone via `changeset version --ignore`) is **not** a remedy available inside a
   release PR. It exists only as a separately authorised pilot (ADR-033); until one is authorised, treat the cascade as the plan.

### 5.2 Published dependency metadata

On the release branch, build and pack **each package in the plan** and inspect the packed `package.json`:

1. No `workspace:`, `file:` or `link:` specifier remains.
2. Sibling `dependencies` and `peerDependencies` are `^<released sibling version>` (ADR-033). An exact sibling pin is an
   exception that needs a recorded reason.
3. Each sibling range is satisfiable by the sibling's version **in this plan** (no range pointing at an unpublished or lower version).
4. For every package whose peer range or sibling range changed, the new range matches the tested versions.
5. For each package whose declarations or manifest changed: the producer validation of ADR-035 (stage 1 workspace declaration
   validation, stage 2 tarball validation) passes when available.

### 5.3 Release ordering and coordination

1. Dependencies precede dependents in the intended publication order. This standard does **not** assume the publish tooling
   orders them; the reviewer records the order **observed in the publish log** (and, before merging, the order intended).
2. For a coordinated release (for example ADR-033's patch release), all packages in the set are in **this** PR, not split across PRs.
3. Mixed old/new populations are acknowledged: published versions are immutable.
4. Decide where the `latest` dist-tag recovery command and the `npm deprecate` text are recorded before merging (recovery is forward-only).

### 5.4 Clean-consumer check for releases that change dependency ranges, peers or distribution

When T2, T3 or T4 applies:

1. Run the clean-consumer verification of ADR-036 §4b (**pnpm 12.16.1**, Node 24+, `strict-peer-dependencies=true`), installing the
   packed release-candidate set so that the installed graph is the graph the registry will serve.
2. Confirm one installed copy and one resolved path of `@comity/primitives`, and that an error from another package is
   an `instanceof BaseError` there and `toSafePayload(err).code` is not `"unknown"`.

### 5.5 Calibration (first uses)

The first uses of this standard record the reviewer's time and the number of false alarms, so that triggers and the T6 threshold
can be set from evidence rather than from the initial guess. The first coordinated release (ADR-033's patch release) is such a use.

## 6. When blocked

The reviewer records the blocking reason. The release owner chooses one of:

1. **Correct the changesets** and let the action regenerate the PR.
2. **Accept and record** an exception (for example an exact sibling pin), with the rationale, in the PR.
3. **Escalate** a design question (for example a split-release pilot, or fixed/linked groups) as a separate decision. A change to
   Changesets behaviour, to the release workflow or to a release script is **never** made inside a release PR.

Manual edits to the generated release branch are discouraged; the action regenerates it.

## 7. Blocking conditions

The reviewer **must not approve** (and the release owner must not merge) when any of these holds:

- A major bump not classified and annotated under §5.1 (the cascade is accepted; an **unlabelled** major is not).
- Any `workspace:`, `file:` or `link:` specifier in a packed manifest.
- An exact sibling pin that is not recorded as an exception.
- A sibling or peer range that no version in the plan satisfies.
- A trigger is present and the full review (§5) is incomplete, or the §4 checklist or its evidence is missing.
- A failing build, test, validation or clean-consumer check on the release branch.
- The plan contains an unrelated or unreviewed package (an unexplained entry in §4.2).

## 8. Evidence to attach

The package table (§4.1), the trigger attestation (§4.6), the packed-manifest listing (§4.4/§5.2), and — when triggers apply — the
major/peer classification (§5.1), the publication order (§5.3) and the clean-consumer output (§5.4).

## 9. Future automation (documented separately, not authorised here)

Candidates, each requiring its own design decision and owner approval: a CI check on the Version Packages PR that fails on
`workspace:`/`file:`/`link:` in packed manifests and on exact sibling pins; a report that evaluates triggers T1–T6 and requires
the attestation; a report that lists peer-triggered majors and requires an annotation before merge; a dry-run job running the
clean-consumer check for range changes; a split-release pilot (ADR-033). None is implemented by this standard.
