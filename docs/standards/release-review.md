# Comity Coding Standards — Release Review of `Version Packages` Pull Requests

> **Provenance:**
> - Authoritative owner: `comity-development`
> - Applies to: every repository that publishes through Changesets (`comity-community`, `comity-development`, future repositories)
> - Status: **Proposed.** Takes effect when ADR-033 is Accepted. Raised with ADR-033 (Commerce / Comity boundary work, 2026-11-04).

A `Version Packages` pull request is generated by `changesets/action` from the pending `.changeset/*.md` files and merging it
publishes to npm. This standard defines the **mandatory human review** of that pull request. It adds no automation and does not
change Changesets configuration or any workflow; those are separate design decisions (see "Future automation").

## 1. Why the review exists

Changesets assigns bumps by rules the author of a changeset does not see:

- Verified with `@changesets/assemble-release-plan@6.0.10` (the version in comity-community): any package that lists a changed
  package in `peerDependencies` receives a **major** bump when that package gets a **minor or major** release, regardless of the
  declared range (and, with `onlyUpdatePeerDependentsWhenOutOfRange`, whenever the new version leaves the range, which every 0.x
  minor does for a caret range). Under 0.x, a major is `1.0.0`. A **patch** of the peered package does not trigger it.
- A sibling dependency with a caret range (`workspace:^`, ADR-033) does not re-release dependents on a sibling **patch**;
  a sibling **minor** re-releases them with a patch bump and moves their ranges.
- `workspace:*` is published as an exact version; `workspace:^` as `^<version at publish>`.

The merge click is the last point at which an unjustified major, a wrong range, or a bad publication order can be stopped.

## 2. Roles

| Role | Responsibility |
|---|---|
| **Release reviewer** | A maintainer other than the author of the triggering changesets, where staffing permits. Completes the checklist in §3 and records the evidence in the PR |
| **Release owner** | Approves exceptions in §5 and decides how a blocked release proceeds |

Approval of the PR is **not** a substitute for the recorded checklist.

## 3. Mandatory checklist

Record the result of each item in a PR comment (or the PR description), with the evidence named.

### 3.1 Release plan

1. List every package in the plan with its old version, new version and bump type. Source: the PR diff of `package.json`
   versions and `CHANGELOG.md`, or `changeset status --verbose` on the merged state.
2. For each package, identify **why** it is in the plan: (a) named in a changeset; (b) re-released because a dependency
   changed (`dependencies`, `devDependencies`, `peerDependencies`). Every package in category (b) must be traceable to a
   changed dependency.
3. For each **major** bump (and each `0.x → 1.0.0`), state the originating changeset or the peer dependency that triggered it.

### 3.2 Peer-dependent bumps

For every package in the plan that lists a changed package in `peerDependencies`:

1. Is the bump **justified by actual incompatibility** with the new version of the peered package (a changed or removed
   contract it uses), or only by the Changesets peer rule?
2. Is the package's own public contract changed? A peer-triggered major with no contract change is an **unjustified major**.
3. Does the peer range in the package's manifest, after publication, correctly express which versions of the peered package it
   was tested against (§3.4)?
4. If a **minor** or **major** of a peered Core Module is in the plan, confirm explicitly how its dependent adapters are
   handled: accepted as a major, or the release is split so that the peered package ships separately and dependents are
   handled by a separate, reviewed decision (§5).

A minor release of a peer package must not silently become an unjustified major release of every dependent package.

### 3.3 Semver classification

1. Each bump matches the changeset text and the actual change (breaking contract → minor under 0.x with a migration note, per the package's ADRs; fix → patch).
2. Releases that change the distribution format or export maps (for example ADR-034) are classified as the ADR states.

### 3.4 Published dependency metadata

On the release branch, build and pack **each package in the plan** and inspect the packed `package.json`:

1. No `workspace:`, `file:` or `link:` specifier remains.
2. Sibling `dependencies` and `peerDependencies` are `^<released sibling version>` (ADR-033). An exact sibling pin is an
   exception that needs a recorded reason.
3. Each sibling range is satisfiable by the sibling's version **in this plan** (no range pointing at an unpublished or lower version).
4. For every package whose peer range or sibling range changed, the new range matches the tested versions.
5. For each package whose declarations changed or whose manifest changed: `declaration-dependencies` validation (ADR-035)
   passes when available.

### 3.5 Release ordering and coordination

1. Dependencies precede dependents in the intended publication order, so that no published version references a sibling
   version that is not yet on the registry for any window longer than the publication run. State the order used by the tooling and the reviewer's confirmation.
2. For a coordinated release (for example ADR-033's patch release), all packages in the set are in **this** PR, not split across PRs.
3. Mixed old/new populations are acknowledged: published versions are immutable.
4. Decide where the `latest` dist-tag recovery command and the `npm deprecate` text are recorded before merging (recovery is forward-only).

### 3.6 Clean-consumer check for releases that change dependency ranges

When the plan changes published sibling ranges or distribution:

1. Install the packed tarballs in a clean consumer (pnpm 10.13.x, Node 24+, `strict-peer-dependencies=true`).
2. Confirm one installed copy and one resolved path of `@comity/primitives`, and that an error from another package is
   an `instanceof BaseError` there and `toSafePayload(err).code` is not `"unknown"`.

## 4. Blocking conditions

The reviewer **must not approve** (and the release owner must not merge) when any of these holds:

- A major bump with no justification under §3.2 or §3.1.3.
- Any `workspace:`, `file:` or `link:` specifier in a packed manifest.
- An exact sibling pin that is not recorded as an exception.
- A sibling or peer range that no version in the plan satisfies.
- A peered Core Module minor or major in the plan with its dependents' bump handling undecided.
- The checklist is incomplete or its evidence is missing.
- A failing build, test, validation or clean-consumer check on the release branch.
- The plan contains an unrelated or unreviewed package (an unexplained entry in §3.1.2).

## 5. When blocked

The reviewer records the blocking reason. The release owner chooses one of:

1. **Correct the changesets** (for example split a minor of a peered package into its own release) and let the action regenerate the PR.
2. **Accept and record** an exception (for example an intended `1.0.0`), with the rationale and the migration note, in the PR.
3. **Escalate** a design question (for example changing how Changesets treats peer dependents, or fixed/linked groups) as a
   separate decision. A change to Changesets behaviour is **never** made inside a release PR.

Manual edits to the generated release branch are discouraged; the action regenerates it.

## 6. Evidence to attach

The package table (§3.1), the peer-dependent analysis (§3.2), the packed-manifest listing (§3.4), the publication order (§3.5)
and, when required, the clean-consumer output (§3.6).

## 7. Future automation (documented separately, not authorised here)

Candidates, each requiring its own design decision and owner approval: a CI check on the Version Packages PR that fails on
`workspace:`/`file:`/`link:` in packed manifests and on exact sibling pins; a report that lists peer-triggered majors and
requires an annotation before merge; a dry-run job running the clean-consumer check for range changes; a Changesets option
or configuration change to treat peer dependents differently. None is implemented by this standard.
